install-packages — five TUI designs

same fixture in all five · render mode labelled per design · every grid verified at its stated column width

Design brief — what this TUI is for

  1. Reconcile. Show what this repo offers against what is on the machine — ~/.claude/, ~/.local/bin, settings.json keys, the plugin cache — and whether each is current. Files compare by content hash; plugins compare by marketplace.json version. A symlink pointing back into the repo counts as always-current.
  2. Select a subset and apply as one batch. Installs, upgrades and removals commit together on a single keypress.
  3. Explain before deciding. Any row can show its description, and some packages carry sample output.
  4. Report per-item outcome. created / updated / removed / already-exists / warning / error, streamed as each item finishes rather than all at the end.

The failure these five are scored against: does the design keep current state and queued action in separate visual channels? Collapsing both into one glyph column is what makes a list like this unreadable — a tick that means “installed”, “current” and “will install” teaches you nothing.

Plugins are included because they already carry real version state; if they should stay out of the TUI, every design below loses 11 rows and nothing else changes.

Plan-then-apply diff

inline80 cols

The list is the plan. Each row carries a + / ~ / - sigil, a totals line states the whole transaction in one sentence, and nothing is written until you confirm. Borrowed from terraform plan and nix-env --dry-run; the unchanged majority folds into a summary so the plan is only as long as the change.

Apply state, mid-stream. Results already arrive per package, so real progress is drawable. r replaces today’s dead-end “press q to exit”.

Smallest vocabulary of any design that still shows removals: three sigils, each its own verb.
State and action cannot collide — an unchanged row has no sigil at all, so the sigil column is purely pending action.
Inline, so the plan and every result line stay in scrollback after it exits.
The totals line makes the destructive step impossible to miss before committing.
The 10 unchanged rows are not selectable until you press a — an extra keystroke on a fresh machine where everything is a delta.
Variable row heights: the explanatory second line appears on some rows only, so the cursor does not advance a fixed distance.
No version columns — “2.1.0 → 2.2.0” is prose in the detail field, not an alignable column you can scan down.

Transaction list

fullscreen120 cols

aptitude’s shape. A read-only STATE column describes the machine; a separate ACT column holds the action you cycled onto that row. The two can never be confused because states are adjectives and actions are verbs, in different columns. Wide, because the version-versus-version comparison is what earns the horizontal space.

Apply state. Only rows that had a queued action appear — the 10 no-ops are not restated.

The only design where the queued action is spelled as a word in its own column. Nothing is inferred.
REPO beside ON DISK makes staleness self-evident without a glyph for it.
Direct-action keys (i/u/d) mean a removal is never one stray space away.
Needs 120 columns. Below that ACTION ON APPLY has to drop — and that is the column carrying the design’s whole argument.
Most keys of any design here: five action keys plus navigation.
Fullscreen, so nothing survives in scrollback; and ACT plus ACTION ON APPLY is arguably one column too many saying the same thing.

Outdated table

inline80 cols

brew outdated / npm outdated: a flat aligned table, no hierarchy, almost no symbols. Staleness reads straight off the two version columns. The bet is that a table you scan in one pass beats any glyph legend — selection is a single checkbox and that is the whole interaction.

The checkbox is desired state; REPO/ON DISK supply the delta. claude-optin shows what an unchecked but still-installed row looks like.

Fewest things to learn: one checkbox, two version columns, no legend at all.
Every row is the same height and every column lands in the same place — no jitter, no expand state.
Inline and copy-pasteable; the table is useful pasted into a message verbatim.
The queued action is never shown. Ten of these boxes are checked and mean “do nothing”; one unchecked box means “delete a file”. They look identical.
A destructive removal is one space away from a row you were only reading, with no confirm.
All 15 rows always render, so the common everything-is-current run is a 24-line wall that says nothing needs doing.
5

Two-channel list

inline80 colsrecommended

The table’s checkbox for intent and the plan’s explicit delta for consequence, in two fixed columns that never share a meaning. Left of the name is what you want; right of the name is what will happen. Current rows have an empty action column, so the queue reads as a shape from four feet away — and the everything-is-current run collapses to about six lines instead of twenty-four.

Default view. Git Utils is the cursor. Note Statusline: [x] with nothing in the action column — checked-and-current is visibly not a change. Its sub-items carry their own boxes, so a partially-installed package (files present, settings.json key absent) shows one sub-row with will install beside it and the parent otherwise untouched — the state useInstaller.ts currently has no way to express.

Results, streaming. The verb leads each line and reuses the wording the selection screen promised: will update becomes updated.

Why this one. The stated goal is a simpler UX, and this is the smallest vocabulary that still keeps both channels apart: a checkbox and a short sentence. No glyph legend, no state words to memorise, no colour that carries meaning on its own.
Two columns, two meanings, no overlap — [x] is always “I want this”; the right column is always “here is the consequence”.
The selection screen’s wording becomes the results screen’s wording, so the same verbs follow you through the whole flow.
Collapses to roughly 14 lines on the common re-sync run, and inline means results stay in scrollback.
A removal-only confirm keeps a delete from riding along on a batch you were not reading closely.
The action column costs ~15 columns of width that design 4 spends on version numbers instead.
The action column must be fixed-width to stay aligned, so a long consequence truncates rather than wraps.
Collapsing the current tail behind a costs one extra keystroke on a fresh machine.
Expanded sub-items break the fixed row rhythm, since only multi-item packages have them.

Colour — every value here has an emission path

Ink and Chalk both accept hex and 256-colour, so these are not limited to the eight the installer uses today. claude-optin already proves the pattern: 256-colour navy 17 and orange 214, each with a reverse-video fallback for terminals without extended colour.
